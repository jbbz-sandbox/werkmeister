# Service registry fragments: a repeatable onboarding process

**Date:** 2026-10-01
**Status:** approved in chat, spec written

## Goal

A new developer clones the team's repos under `paths.repos_root`, runs
`npx @jbbz-sandbox/sandbox-cli setup`, and ends up with a
`~/.sandbox/services.yaml` that already knows every service in those repos.
Nobody copies a teammate's registry; nobody hand-writes entries for a repo
that already describes itself.

## Problem

`~/.sandbox/services.yaml` is machine-local and hand-edited. `sandbox setup`
seeds it exactly once, with either the demo apps or an empty commented
skeleton (`scaffold.ts` `renderServicesYaml`), and never adds entries for any
other repo. There is no place where team-owned service definitions live, so
every new machine starts from zero and every registry drifts from the next.

Helm charts were considered as a source and rejected as insufficient: a chart
gives `internal_port`, `health_endpoint` and the `k8s_*` coordinates, but not
the dev `image`/`command`, `port_offset`, `setup_service`, `archetype`,
`test`, memory limits, `depends_on`, `feature_router` or the sandbox-side
`environment` values. Those are decisions a human makes once, next to the
code, and the fragment is where they are recorded.

## Design

### 1. The fragment: `<repo>/.sandbox/services.yaml`

Each app repo commits a fragment that is a literal slice of today's registry
schema, limited to these top-level keys:

| Key | Meaning |
|---|---|
| `services:` | Same per-service schema as the registry (`docs/users-guide.md` "services.yaml"). |
| `setup_services:` | Same schema as the registry. |
| `infrastructure:` | Same schema as the registry. A repo that depends on a cluster-forwarded datastore declares it here. |

Rules:

- `repo:` on a service defaults to the checkout's directory name under
  `repos_root`. When written it must equal that name; a mismatch fails the
  merge.
- `repos:` is never written by hand. Sync derives it: for each repo, the list
  of its services and `path_mappings: {<path>: <service>}` from each
  service's `path`. A service with `path: .` contributes no path mapping.
- Any other top-level key is an error, except `x-*` keys, which are ignored
  (they exist to hold YAML anchors, as `x-mcp-client` does today). Anchors are
  resolved when the fragment is parsed, so they never cross fragments.
- Comments live in the fragment. The generated registry carries none.
- Placeholders `{{home}}`, `{{repos_root}}` and `{{workspaces_root}}` expand
  in every string value from `os.homedir()` and `config.yaml` `paths` at
  merge time. No other `{{...}}` or `${...}` text is touched: the registry
  already carries `${CONTEXT7_API_KEY:-}` (expanded by the MCP client) and
  `${SANDBOX_MCP_TOKEN}` (deliberately never expanded on the host), and a
  merge-time expander must not interfere with either.

The sandbox repo's `.gitignore` ignores `.sandbox/` wholesale (the CLI writes
generated files there when run from the checkout); it gains
`!.sandbox/services.yaml`. demo-services and wellness have no such rule.

### 2. The merge: `packages/sandbox-core/registry_sync.ts`

One module, pure functions over parsed documents, plus one function that
touches the filesystem.

`discoverFragments(reposRoot): Fragment[]` scans `repos_root` one level deep
for `<dir>/.sandbox/services.yaml` and returns `{ repo, path, doc }` for each,
sorted by repo name so output is stable.

`mergeRegistry(fragments, { defaults, local, paths }): MergedDoc` layers, last
wins:

1. **Sandbox-owned defaults** from `scaffold.ts`: `archetypes` and
   `mcp_servers`, exactly the content `servicesPreamble` emits today, kept as
   data (an object) rather than text.
2. **Every fragment**, after placeholder expansion and `repo:` validation.
   Collisions fail loud, naming both repos and the key:
   - the same service name in two fragments;
   - the same setup service or infrastructure name in two fragments;
   - the same `port_offset` on two services, across all fragments;
   - the same `k8s_forward_port` on two services or infrastructure entries.
3. **`~/.sandbox/services.local.yaml`**, the per-machine hand-edit file. Any
   top-level key is allowed; maps deep-merge over the result, scalars and lists
   replace. `k8s_context` lives here. Setup seeds it once with
   `k8s_context: <answer>` (default `orbstack`) using `seedFile`, and never
   touches it again.

`renderRegistry(merged, sources): string` emits a header comment:

```yaml
# GENERATED by `sandbox registry sync` — do not edit.
# Sources: <repos_root>/demo-services/.sandbox/services.yaml,
#          <repos_root>/sandbox/.sandbox/services.yaml
# Machine overrides: ~/.sandbox/services.local.yaml
```

followed by `yaml.stringify` of the merged document in this key order:
`archetypes`, `mcp_servers`, `k8s_context`, `services`, `infrastructure`,
`setup_services`, `repos`.

`syncRegistry({ reposRoot, checkOnly }): Step[]` ties it together and returns
setup-style steps:

- no fragments found → one failing step: "no `<repo>/.sandbox/services.yaml`
  under `<repos_root>` — clone your team's repos there and re-run
  `sandbox setup` and answer yes to the demo apps". The registry is not written.
- merge error → one failing step carrying the error message.
- `checkOnly` → compare the rendered text to the file on disk; ok when equal,
  failing "drift: would rewrite" when not or when the file is missing.
- otherwise → write. If a file exists without the `# GENERATED` header, copy
  it to `services.yaml.bak-<unix-seconds>` first and say so in the step
  detail. A file with the header is overwritten silently.

### 3. Commands

- `sandbox setup` runs `syncRegistry` as a step **after** the repo clone
  steps (today `syncRegistryConfigs` runs before them; the demo-services
  fragment must be on disk first). `syncRegistryConfigs` keeps seeding
  `ports.yaml` and `model-pricing.yaml`, and gains `services.local.yaml`
  (seeded once with the wizard's `k8s_context` answer); `services.yaml` leaves that list and
  the legacy `infra/config/services.yaml` migration is dropped (a migrated
  file would be backed up and regenerated on the same run).
- The demo-services clone is gated on the wizard's demo answer (there is no
  `--demo` flag; `--yes` takes the default, which is no) **or** the repo
  already being present under `repos_root`, replacing today's gate on the registry
  mentioning it (the registry does not exist yet at that point).
- `sandbox registry sync` runs the same function on its own, for the moment
  a developer clones a new repo and wants it registered without a full setup.
  `sandbox registry --check` reports drift with a nonzero exit, like
  `sandbox config --check`.
- The wizard's "4. Service registry" section no longer asks about an existing
  file; it lists the fragments found and says the registry will be generated
  from them, or that none were found and asks whether to clone the demo apps. The `k8s_context`
  prompt stays and feeds `services.local.yaml`.

### 4. Readers do not change

Every loader in `config.ts`, the compose generator, `detect`, `init-workspace`,
the MCP server and the dashboard keep reading `~/.sandbox/services.yaml`.
`loadReposConfig()` keeps working because the merge emits `repos:`.
`getK8sContext()` keeps working because the local overlay supplies it.

A load-time merge inside `servicesDoc()` was considered and rejected: every
reader would pay the scan, there would be no inspectable artifact, and
`--check` drift reporting would be meaningless.

### 5. Scaffold changes

`renderServicesYaml`, `servicesPreamble`, `demoServices` and `emptyServices`
are deleted from `scaffold.ts`. What replaces them:

- `REGISTRY_DEFAULTS` (object): the `archetypes` and `mcp_servers` content.
  The explanatory comments from the preamble move to the users guide.
- The commented example that `emptyServices` printed becomes the "Writing a
  fragment" section of `docs/users-guide.md`, with the placeholder rules.
- `renderServicesLocalYaml(k8sContext)` for the one-time seed of
  `services.local.yaml`.

### 6. Migration

Three PRs, in this order:

1. **sandbox**: `registry_sync.ts`, setup and wizard changes, the `registry`
   command, scaffold cleanup, `.sandbox/services.yaml` for the five
   self-host services with `/Users/jayboyer` replaced by `{{home}}` and the
   `x-mcp-client` anchor block moved in with them, the gitignore negation,
   users-guide updates, a changeset.
2. **demo-services**: `.sandbox/services.yaml` holding `backend`, `frontend`,
   `demo-install`, `redis`, `postgres`.
3. **wellness**: `.sandbox/services.yaml` holding `api` (NestJS,
   `internal_port` 4000, `port_offset` 7, `/health`, `k8s_port` 80, secrets
   from `apps/api/.env`) and `mobile` (`expo start --web`, `internal_port`
   8081, `port_offset` 8, `/`), plus a `wellness-install` setup service
   mirroring `demo-install`. Offsets 0-6 are taken by demo-services and
   sandbox.

On the author's machine the first `sandbox registry sync` backs up the
current registry and regenerates it. Acceptance for PR 1 is that the parsed
document of the regenerated file equals the parsed document of the backup
once `repos:` ordering and the absence of `x-mcp-client` are accounted for.
`k8s_context` and nothing else lands in `services.local.yaml`.

### 7. Testing

`packages/sandbox-core/registry_sync.test.mjs`, in the existing
`node --test *.test.mjs` style, against a temp `repos_root`:

- two fragments merge; `repos:` is derived with correct `path_mappings`;
  defaults are present; key order is as specified.
- each collision type (service, setup service, infrastructure, `port_offset`,
  `k8s_forward_port`) fails and the message names both repos.
- a `repo:` that disagrees with the directory name fails.
- placeholders expand; `${...}` strings pass through untouched.
- the local overlay wins over a fragment and supplies `k8s_context`.
- `checkOnly` reports drift when the file differs or is missing.
- a header-less existing file is backed up before the write; a header-bearing
  one is not.
- no fragments → failing step, nothing written.

`machine_setup` tests gain: the registry step runs after the clone steps, and
the demo clone is gated on the demo answer or on-disk presence.

## Out of scope

- Cloning repos setup has not been told about (a repo list in `config.yaml`
  or GitHub discovery). Decided against for now; nothing here blocks it.
- Automatic `port_offset` allocation. Offsets stay explicit; collisions fail.
- A chart-reading drafter for new fragments. The users-guide example plus the
  chart-to-field table above is the "how do I fill this in" story.
