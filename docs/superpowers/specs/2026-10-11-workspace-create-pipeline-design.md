# One workspace-create pipeline: issue copy, shared issue section, tracker auth

Status: design approved in conversation 2026-10-11; awaiting spec review.

## Problem

Every entry point already ends in `provisionWorkspace` (`packages/sandbox-core/workspace_init.ts:832`), but reading
the issue happens before core, in some front-ends only:

| Entry point | Fetches + distils the issue today |
|---|---|
| `--browser-form`, MCP `workspace` / `issue-form-data`, pane "Fill from issue" | yes (pane on the session model, the rest via `claude -p`) |
| `sandbox workspace <feature> --issue-id X` with flags, terminal wizard, MCP `create-workspace`, apps/mcp `sandbox-workspace` | **no** |

Then the strategies render whatever arrives differently. JIT `CLAUDE.md` links the issue; ICM `CLAUDE.md` and
`BRIEF.md` never mention it. No workspace stores the issue itself: the briefing lives only in
`~/.sandbox/issue-cache.json` for 15 minutes.

Observed 2026-10-11: eight ICM workspaces created with the direct CLI (the path `sandbox-workspace` SKILL.md
recommends "if the user already gave every input") got a placeholder `BRIEF.md` and no reference to their issue.

## Goals

- One create entry point shared by the CLI, both MCP servers, the pane and the skills, for JIT and ICM alike.
- An issue-backed workspace always holds its issue and always points back to it. No caller can skip this.
- Same inputs + same issue snapshot → byte-identical generated files.
- `sandbox connect` checks the issue tracker and helps the person sign in.

## Non-goals

- Making the model rewrite deterministic. It stays an optional addition; the issue copy is the source of record.
- Changing the ICM stage contracts or JIT skills beyond the issue section.
- Auto-refreshing the issue copy.

## Decisions

| Question | Decision |
|---|---|
| What does the brief rest on? | A fixed issue copy saved verbatim at creation; the model rewrite fills empty fields when available. |
| Issue can't be fetched | The create fails and nothing is created. |
| When does the copy update? | Frozen at creation; `sandbox init-workspace --refresh-issue` refreshes it. Instructions tell the agent to re-read the live issue before each stage. |
| Where is the rule enforced? | In core's single `createWorkspace`; front-ends cannot skip it. |

## 1. Core pipeline

`createWorkspace(inputs, opts)` in `packages/sandbox-core/sandbox.ts` is the one public create function. The CLI
command stops calling `provisionWorkspace` itself, which also removes the cwd-vs-`$HOME` input-resolution drift.

`opts`: `{ open?, distill?: false | ((prompt: string) => Promise<string | null>), cwd?, readStdinTask?, force?, onData?, signal? }`.
`cwd` defaults to `$HOME`; the CLI passes `process.cwd()`.

Steps:

1. `resolveInputs` — unchanged.
2. `resolveIssue` (new, only when `issue_id` is set):
   - `tracker.parseRef(issue_id)`; no ref → fail.
   - `tracker.fetchIssue(ref)`; null → fail with `couldn't read <ref> from <tracker>` plus the `checkAuth` fix line when
     sign-in is the cause.
   - Returns `IssueSnapshot { ref, url, tracker, title, status, body, comments, fetchedAt }`.
   - Fills `task` from the title when empty.
3. `distill` (optional): runs when `description` or `starting_prompt` is still empty and `opts.distill !== false`.
   Builds the prompt with `buildIssueExtractPrompt`, runs `opts.distill` (default `askClaude`), applies with
   `applyIssueFormAnswer`, and fills only empty fields. Failure → warning, creation continues.
4. `provisionWorkspace(resolved, { issue })` — worktrees, then `initWorkspace`.
5. `initWorkspace` writes `.sandbox/issue.md` from the snapshot before `strategy.init`, and passes it as
   `InitContext.issue: IssueSnapshot | null`.

Re-init (`sandbox init-workspace`) reads the snapshot back from `.sandbox/issue.md` and never fetches.
`--refresh-issue` re-runs step 2 and rewrites the copy; it does not re-run step 3.

## 2. Issue copy and shared issue section

### `.sandbox/issue.md`

```
---
ref: jbbz-sandbox/sandbox#120
url: https://github.com/jbbz-sandbox/sandbox/issues/120
tracker: github
status: open
fetched: 2026-10-11T18:04:00Z
---
# <title>

<body, verbatim>

## Comments

### <author> · <date>

<body>
```

Every comment, uncapped. Generated by sandbox, never hand-edited; its frontmatter is what re-init parses.

### `renderIssueRef(issue)` — new `packages/sandbox-core/strategies/issue_section.ts`

```
## Issue

[<ref>](<url>): <title>. Copy taken <date>: `.sandbox/issue.md`.
Before each stage, re-read the live issue for newer direction: `sandbox issue view`
```

`sandbox issue view` (`apps/cli/src/commands/issue.ts`) already reads either tracker and, with no ref, reads the
workspace's own `issue_id`, so the section names one command for every tracker.

| | Issue section | Brief / first instruction |
|---|---|---|
| ICM | root `CLAUDE.md`, plus a "Where things live" row for `.sandbox/issue.md` | `BRIEF.md` = issue section, then `description`, then `starting_prompt`. The "No starting prompt was given" note (`icm.ts:213`) appears only with no issue and no prompt |
| JIT | `CLAUDE.md` Current Task, replacing today's bare link | starting-prompt handoff note opens with the issue section; written even when `starting_prompt` is empty, if there is an issue |

A workspace without an issue renders as today.

## 3. Tracker auth and `sandbox connect`

New `IssueTrackerStrategy.checkAuth(): Promise<{ ok: boolean; who?: string; fix: string }>`:

- GitHub: `gh auth status --hostname github.com`, then `gh repo view <repo>` for each of `githubIssueRepos()` to catch a
  token without repo access. Fix: `gh auth login` / `gh auth refresh -s repo`.
- Jira: `GET /rest/api/3/myself` with the configured token. A placeholder `base_url` (`JIRA_PLACEHOLDERS`) counts as
  not configured — this also resolves #114 at the root. Fix: `docs/jira-rest-setup.md`.

`sandbox connect` runs it after infra and prints `issue tracker · <id> · ok (<who>)` or `… · <reason>`.

- On a TTY, a failed GitHub check offers "Sign in to GitHub now? (gh auth login)" and hands `gh` the terminal, then
  re-checks. Jira prints its steps. Credentials go only into the tracker's own prompt.
- Without a TTY (pane, MCP, `--k8s`) it reports only.
- A failed tracker check does not fail `connect`.

Pane: the infra line gains `· tracker: <reason>` on failure, from `checkAuth`, cached 5 minutes.

## 4. Entry points, instructions, backfill

- CLI `sandbox workspace`: goes through `createWorkspace`; new `--no-distill`. The wizard runs `resolveIssue` + distill
  right after `issue_id` and defaults later prompts to the filled values.
- `--browser-form`: forwards every flag given (today only `--issue-id`, `--open`); CLI values pre-fill the form.
- MCP `create-workspace`, `workspace` (`apps/sandbox-dashboard/server.ts`) and apps/mcp `sandbox-workspace`: call
  `createWorkspace`; descriptions say the issue is fetched and stored; stale "spawns `sandbox workspace`" text removed.
- Pane: "Fill from issue" stays as an editable preview; Create passes a `$.model.complete`-backed `distill`; core skips
  fields the preview filled. Drop `repos` from the `workspace_form` tool description.
- Skill `plugins/sandbox-tools/skills/sandbox-workspace/SKILL.md`: one rule — every create goes through
  `createWorkspace`, never hand-write workspace files. Paths: direct CLI (issue fetched for you; `--task` only to
  override), form for review, batch = one CLI call per issue, in sequence, then check each has `.sandbox/issue.md` and
  a `BRIEF.md` naming its issue. Fix the MCP tool name (`mcp__plugin_sandbox-tools_sandbox-workspace__workspace`).
- Docs: `docs/context-strategies.md` (part 2 table), a "Creating a workspace" section in `docs/users-guide.md`, stale
  comments in `sandbox.ts:1-14`, `server.ts:133-139`/`:216-218`, `form-cli.ts:13`, `workspace_prompts.ts:365-367`.
- Backfill: `sandbox init-workspace --refresh-issue` in each issue-backed workspace writes `.sandbox/issue.md` and
  updates `CLAUDE.md`. `BRIEF.md` stays write-once, except that a brief still exactly equal to the placeholder is
  rebuilt; an edited brief is never touched.

## 5. Errors

| Case | Result |
|---|---|
| `issue_id` doesn't parse | fail before any worktree: `<ref> isn't a <tracker> issue ref (e.g. <refExample>)` |
| fetch fails | fail before any worktree, with the `checkAuth` fix when sign-in is the cause |
| rewrite fails / no model | continue; warn `description/starting_prompt not filled from the issue: <reason>` |
| `--refresh-issue` fetch fails | keep the old copy; command fails |
| `issue.md` missing on re-init | issue section renders from `issue_id` (link + re-read command) with "no stored copy; run `init-workspace --refresh-issue`" |

Also: quote `DESCRIPTION` (or flatten to one line) when writing `.env` (`generate.ts:286-288`), since distilled
descriptions can be multi-line.

## 6. Testing

Stub tracker, no network.

- sandbox-core:
  - `createWorkspace` end to end in a temp dir: issue → `issue.md` written and issue section in both strategies; fetch
    failure → nothing created; distill failure → created; caller-filled fields never overwritten.
  - Repeatability: same snapshot + inputs, run twice → byte-identical files for JIT and ICM (timestamp fixed).
  - `renderIssueRef` snapshots for GitHub and Jira.
  - `--refresh-issue`: replaces the copy; keeps it on fetch failure; rebuilds only a placeholder brief.
  - `checkAuth` for both trackers, including the Jira placeholder `base_url`.
- CLI: `sandbox workspace` goes through `createWorkspace`; `--no-distill`; `--browser-form` forwards all flags;
  `connect` prints the tracker line.
- Pane: Create passes the session-model distill; tracker failure on the infra line.
- Consistency guard: a test fails if any `apps/*` or `plugins/*` source calls `provisionWorkspace` or `initWorkspace`
  directly for a create.
