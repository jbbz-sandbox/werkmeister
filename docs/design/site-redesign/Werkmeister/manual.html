Field manual / Start here

Quick start

Take one ticket from your tracker into a running workspace, then through review and release.

Before you begin

Have Git, Node.js 22 or later, and an OCI container runtime with Docker Compose v2 available. Choose an agent harness such as Claude Code, Codex, or OpenCode. You can connect Jira, GitHub Issues, or a custom tracker.

Set up your machine

Run the setup wizard from your home directory. It installs the CLI, asks where your repositories live, and configures services, local routing, and your issue tracker.

cd ~
npx werkmeister machine setup

Setup asks for elevated permissions when configuring the local TLS certificate and host entries. The Claude Code plugin step requires claude on your PATH.

Create a workspace

Use your own issue ID in place of SW-123. Werkmeister copies the ticket into a new workspace and creates code worktrees on a dedicated branch.

werkmeister workspace new my-feature --issue-id SW-123

Open the new workspace folder in your harness, or choose Start on the workspace card. The agent follows the instructions and stages for this kind of work.

Review and close

When the workflow asks for a decision, read the stage output and approve it or request changes. Once you approve the PR draft, the agent runs werkmeister pr open to check the work, push the branch, and open the pull request.

You review and merge the PR. After the change ships, the agent records a short retrospective and runs werkmeister workspace close to close the ticket and clean up its workspace.

Field manual / Start here

Workspace lifecycle

Each ticket has its own working directory and a record of the decisions that carry it through release.

Follow the state

Werkmeister reads the workspace’s PR files to determine its state. More than one code repository can participate in the same ticket.

Working
The agent is working. PR files may still be drafts.
Ready
All PR files have been approved.
PR open
At least one pull request has opened in a code repository.
Merged
Every pull request has been merged or progressed further.
Shipped
All PR files have shipped, closed, or been abandoned.
Closed out
The workspace has its close-out record.

Read the gate

Approval records a person’s decision on the PR draft. The gate checks the evidence for opening it, including acceptance criteria, the state of the worktree, tests for changed services, and evidence that the running change was exercised and reviewed.

werkmeister pr gate

This command reports the checks. When the agent runs werkmeister pr open, it checks them again before opening the pull request.

Merge and release

You decide when to merge. The code worktree supplies the pull request, while the workspace root branch holds its record. Once every PR is shipped, closed, or abandoned, close-out can record the outcome and remove the workspace.

Field manual / Architecture

Request routing

Run the services a ticket changes on your machine. Let the rest of the application come from a shared baseline.

Select a workspace

A local Caddy reverse proxy receives requests for your configured service hostnames. Select a feature in the browser at /__werkmeister or send its name in an X-Feature header.

curl -H 'X-Feature: checkout-retry' \
  https://frontend.local.werkmeister.io/

The example uses the project’s sample frontend hostname. Your own registry defines the hostnames and services available to the proxy.

Resolve the service

↳

Changed service

A matching feature container receives the request through its published local port.

↳

Baseline service

A service without a matching local container uses its configured upstream. That may be a local baseline, a remote host, or a shared cluster via port-forwarding.

Understand isolation

Each feature has its own code worktrees, containers, and routing identity. Features can still use the same baseline database and Redis service. That distinction matters when testing changes that write shared data.

Running the feature containers and their tests works without Kubernetes. Cluster intercepts are optional and require a configured cluster.

Field manual / Reference

CLI commands

Use werkmeister or its short name, w9r, to manage workspaces, inspect services, and prepare pull requests.

Discover commands

Ask the CLI for its command groups, then request help for an individual command to see the options supported by your version.

werkmeister --help
werkmeister workspace new --help

Workspaces and services

List your workspaces from anywhere. Use the feature commands in the workspace you want to inspect.

werkmeister workspace list
List feature workspaces on this machine.
werkmeister feature up
Bring up the workspace’s declared services.
werkmeister feature status
Inspect the state of its feature containers.
werkmeister feature logs
Read the running feature’s container logs.

Pull requests

werkmeister pr gate
Check whether the PR draft and workspace meet the opening requirements.
werkmeister pr open
Run the gate, push the code branch, and open the approved PR.
werkmeister pr status
Refresh the recorded state of the workspace’s PRs.

Field manual / Reference

SDK guide

Build local tools on werkmeister-core/sdk, the public interface for reading workspaces and running workspace actions.

Match your CLI version

Use Node.js 22 or later. Look up the version of your installed CLI and install the matching release of werkmeister-core. The project's versioned public API is the /sdk entry point.

werkmeister --version

Read a workspace

Run this JavaScript module on the machine holding the workspace directories. Listing workspaces and reading their current ICM stages happen locally and do not require the daemon.

import { icmStage, listWorkspaces } from "werkmeister-core/sdk";

const { workspaces } = await listWorkspaces();
for (const workspace of workspaces) {
  const stage = await icmStage(workspace.path);
  console.log(workspace.name, stage?.name ?? "No ICM stage");
}

Call the daemon

Some operations run in the local daemon. The SDK’s callTool helper sends an authenticated request and returns the tool result. A browser interface should call a local server that uses the SDK, since the daemon rejects requests carrying a browser origin.

Field manual / Project

Why Werkmeister

The project began with a team in Pune, a time difference, and new developers waiting days for a working environment.

The first problem

In the founder’s account, setting up a new engineer meant assembling about ten local containers. A question raised in one office often waited until the other came online.

The first version ran only the services a developer was changing and drew the rest from a shared environment. The founder reports that onboarding went from days to about half an hour for that team.

From one ticket to many

The original environment handled one feature at a time. Switching to a bug meant tearing down the feature and bringing it back later. Giving every ticket its own worktree and running services allowed several changes to progress side by side.

Agent workflows added another question for the design. When several agents are working, how does a developer find the one that needs a decision? The workspace view surfaces those questions alongside the status of the other tickets.

The name

Werkmeister is a German term for a workshop foreman. A foreman knows what is happening at each bench and when a job needs attention. The short command w9r counts the nine letters between the first and last letters of the name.
